# R139 — When a consolidation pass pays

When a consolidation pass pays: context per change, measured, against the work the roadmap says is coming. The person, 2026-10-31: "consider when it is net beneficial to refactor the code. I just have a strong intuition that [at] a certain size of project. It is more beneficial to pause future work and go through the entire project to improve the efficient, readability and most important minimizing, bloat, and improving elegance of the code for future development ... I don't care how human readable it is, but I want it to be maximally token efficient for agents to work on, and of course, when effective to optimize for performance ... It has to not be so code code oriented as well. I wonder if the essence of this though has an underlying principle that would be universal for any complex project." Then: "every project as it works through a few roadmaps can make a pretty smart knee jerk guess just based on the description of the roadmap alone whether or not roadmap three is going to be more work than roadmap two, and if roadmap two is done, then it has easy to access statistics on the work that was done to make smart determinations on refactoring". Agent's reading: the universal measure is context per change, how much an agent must take in to change one thing correctly; a pass pays when its cost is below (context saved per change x changes still to come) + rework avoided, and the remaining roadmap is the changes still to come. Two passes with different triggers: structure for agents (universal, by context per change) and performance (per project, by a measured number the person or users feel). Findings first: (a) context per change for colony and Bookflow over time, from transcripts and git, against their size; (b) where agents' reading goes (hotspots: read cost per change by file); (c) whether the cheapest model can rank an item's size from its text alone, calibrated on finished items. Only if they hold does a check get designed (at a milestone's end, a suggested pass for the person to take or skip, with the hotspot list, its payback measured after). Not a whole-project pass by size alone, and nothing pauses on its own. Then, on milestone ends as the moment: "I think your consolidation pass at milestone end is a phenomenal way of doing that. I think the only thing we need to make sure is that we trust that milestones will be consistently produced in general locations where this structure is beneficial". Agent's reading, on the two roadmaps: milestones are not regular (colony's run 1 to 22 items, Bookflow's 5 to 52, and colony's M2 has stayed open a month as a theme), so the check runs at every finished item (arithmetic on numbers colony already keeps, no model) and speaks only when the payback is clear, suggesting the pause at the nearest seam: a milestone's end if one is a few items away, otherwise between two items, never mid-item. The person also noted the visible roadmap undercounts what is coming (it may double as they playtest): so each project's own growth rate is measured, and the decision is framed as payback time at the current pace against the project's expected life, which unknown future items barely move. Findings (2026-10-31, design/r139-context-per-change.md, read-only, 6 Haiku calls): context per change has not grown with size in either project (Bookflow 83-95 tokens of project reading per changed line while it grew 144k to 269k lines; colony 100-190, no trend, 13k to 38k). Reading the project is a minority of input (23% colony, 34% Bookflow, re-reads counted); start-up instructions 8-13%; the rest (53-69%) is the agent's own conversation (command, test and git output, its own words), which restructuring code cannot remove. Hotspots: board.py is 23% of colony's reading because 444 of 988 commits touch it, not because it costs more per change; Bookflow's largest sink is four guidance documents every helper reads at start (14% of its reading). Payback: Bookflow's start-up documents about 0.6 weeks (0.2-2), board.py about 7 (1-120). Roadmaps grow: milestones ended 2.7x (colony) and 1.8x (Bookflow) their planned size, 0.78 and 0.64 items added per item finished, about half changes to existing features. Size from text alone: Haiku ranked Bookflow items at +0.60 against actual cost, colony's at +0.20 (noise; its costs are split from the lead's activity). Codex reads about 6x more project material per input token than Claude Code. Agent's reading: no evidence for a whole-project pause at a size; targeted passes on hotspots pay, and the first hotspot is documents, not code. Then the person, 2026-11-01: "R139 - should we consider if this kind of maintenance should be baked into each projects refactoring check?" Agent's reading: yes: the findings held (targeted passes pay; the first hotspot is documents), so the check gets designed, and it measures read cost per file whatever the file, code or guidance documents alike, start-up documents weighing most since every session pays them; Bookflow's four start-up documents become its first case, raised by Bookflow's own check rather than a one-off message (that question is superseded unless the person wants Bookflow to have it sooner); R140 was the same maintenance done by hand on colony's own instructions. Next, once R141's round settles: design and build the per-project check (at every finished item, from numbers colony keeps; speaks only at clear payback; suggests the pass at the nearest seam for the person to take or skip), checked by replaying colony's and Bookflow's history and confirming it flags Bookflow's documents and stays quiet where nothing pays. Built and live 2026-11-01 (9eaf5dc; design/r139-check.md): colony/cleanup.py reads what each project's sessions read (Claude Code and Codex transcripts, from a cursor every 2 minutes), finds hotspots (start-up documents read by a fifth of sessions, or a file over 5% of reading), and at a finished item, when the worst-case payback is under 4 weeks, within the work to come and saves at least 1% of reading, leaves the agent one note for one gate at the nearest seam (default: skip and carry on); suggestions, answers and a taken pass's measured payback go in .board/cleanup.jsonl. Replayed over 221 finished items it would have spoken once: Bookflow after R10 (start-up docs, 12% of reading, payback about 0.7 weeks); colony never (board.py 2.7 to 36 weeks central). Bookflow's live case today is marginal (method.md and m4-rules.md, about 1.1% of reading saved against the 1% floor); estimates stay uncalibrated until a first pass is taken and measured. The token lever is the instructions and files carried every step and the number of steps, which this check and R140 address. 2026-11-01, a cross-project token study (14 days, every transcript): the one big lever was helpers' prompt cache: Bookflow's helpers waiting on ~10-minute test loops rewrote 200-400k contexts at each resume under Claude Code's 5-minute helper cache; the 1-hour cache nets about 11% of all colony spend (others lose 0.1-0.2% each), so Claude consoles now start with it (provider console_env). Colony's carry-on nudge no longer wakes a lead while its helpers or background work run (Bookflow: 80 nudges, 69 ending within three steps). Open, each to be measured or blind-tested before acting: Bookflow helpers living to 250-500k contexts (hand off near 250k: 3-5%, a quality trade-off); leads running to 1M contexts (an autocompact cap: about 2%).
