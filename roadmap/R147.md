# R147 — Research in a locked room

The person, 2026-11-02, relayed by Memory Research (m1a6b4d6e): "We need to posture these agents to be rather paranoid of prompt injection, and we probably should give them a limited system access so that they literally can only produce a deliverable of information back to the requested agent"; "there's a lot of prompt injection concern here we need to consider"; "Because this is eventually going to be proposed as an integration to colony, we should also propose the colony produce and established in standardized retrieval method provide provider specific for safe research and searching."

My reading: R75 (research reads, never acts) grown into one locked-down runner that every web research in colony goes through: Q Branch's passes first, then colony's research helpers and the monitor's scout. The contract: prompt in, text out; a generic subject only, no project context; no writing, no commands, no logged-in accounts; pages kept in a per-run workspace for audit; every tool call logged; output parsed by code; anything handed to an agent with tools screened first (seeded from Q Branch's instruction-like-text filter, plain-text cap and cheap screen). Division agreed with Memory Research: colony owns the runner, the provider profiles (colony/providers.py, PROVIDER:), the sandbox, logs, parsing and the hand-off screen; Q Branch owns the research method, the source tools, the source index and its vote ledger.

Evidence (Memory Research's r33 logs): Claude's profile works today (`claude -p --tools WebSearch --strict-mcp-config`, only the source server, `--setting-sources project`, an empty folder: no Bash, Read or Write). Codex isn't safe for research yet: its GitHub connector ran as the person (13 of 36 passes), browser and computer use are on, and its shell can't be switched off and reads any file in read-only mode, so a hijacked pass could leak local files through a URL. Codex stays judge-only with search off.

Sandbox: bubblewrap as the base layer, binding only the workspace (writable), the CLI and its runtime (read-only) and the network; never / as a whole, since four of Codex's bwrap sandboxes binding / have hung in mount locking for 18 days here beside a hung NTFS drive. A time limit stops and reports a hung run. The CLI's login stays readable only by the CLI: research runs only on profiles with no shell.

Left for the person once it runs: whether agents' own web reads inside their sessions also move onto it (it would change how every agent works).

Check: a pass told by a planted page to read a local file or call out with project text can't do it (the attempt shows in the log, the screen flags the page), and Q Branch's briefs run through it unchanged.

The hand-off screen's seed arrived (m7d74ba57, Memory Research's qbranch/ at 134a3c8: screen.py, prompts/screen.md, 17 tests), from the person's ask to it, as relayed: "a smart way to screen deliverables for anything web based ... a smart handoff that if we do correctly is provider [agnostic]". Shape: JSON in, `{text, envelope, report}` out, exit 0 delivered or 5 held. Layer 1, code: strips zero-width and bidi characters, hidden HTML, data URIs and long base64 runs, drops lines addressed to an AI, lists commands named and uncited links. Layer 2, a cheap model on any runner: the deliverable inside a random fence, the model may only return exact quotes to cut with a reason, code applies them (a hijacked screener can over-cut or miss, never add); a malformed reply holds the deliverable (fail closed). One envelope for every provider ("UNTRUSTED RESEARCH FROM THE OPEN WEB, screened <date>...", what was removed, the commands named, the text). Its source tools are now logged-out GitHub REST (public data only), and its Codex runner turns off connectors, browser and computer use.
Memory Research suggests screening on a different provider from the one that produced the deliverable, since a trick aimed at one model rarely works on another. My reading: by default that would put Codex in every brief's path, against the reservation (u05d51bcc); the build screens on a different Claude model from the pass (the cheap tier against Sonnet), and cross-provider screening is offered as a setting where a project has both and the person allows it. To review at the build: whether layer 1's AI-addressed-line filter cuts legitimate how-to text, and the fence's handling of a deliverable that quotes the fence pattern.
Both review points answered by Memory Research (m7ebfd169, fixed in 854c525, local probes, no model calls): (1) layer 1 had used the core's broad injection pattern and cut 9 of 10 ordinary how-to lines ("put it in the system prompt", ".gitignore rules"); it now drops only wording that makes sense solely as an attack on a reading model ("ignore all previous instructions", "If you are an AI assistant,"), the rest going to layer 2 (its own probe set: 16 legitimate lines kept, 7 attacks dropped; add colony's own cases at the build). (2) The model's fence was sound (48-hex random token per chunk, regenerated on collision), but the receiver's envelope had no end, so a forged "END OF UNTRUSTED RESEARCH" could pose as text after the research; the envelope now names a random end token in its first line and closes with it. Agreed default: screen on a different Claude model from the pass, cross-provider a setting.

## Built

2026-11-06, after the weekly reset (b85e410 and 5a97d3a, merged 7b21db4; DNS fix 45e37a7; deployed). `colony/room.py`'s `research()` is prompt in and text out. Each run has a folder under the board's home (`room/<id>/`) holding the prompt, `log.jsonl` with every event, the result and the screen report, pruned after 30 days. `colony room` takes a prompt on stdin. The scout now runs through the room, so the monitor's scout is screened and enveloped.

Claude's profile runs only WebSearch and WebFetch, under bubblewrap:
- a clean environment;
- the claude binary and its libraries read-only;
- the CA bundle, nsswitch and gai.conf;
- its own resolv.conf (public resolvers) and hosts, so a pass can't resolve tailnet or home-network names. The board is served under one, which I found at review;
- the workspace as its cwd and HOME;
- only `~/.claude/.credentials.json` bound read-only.

It never binds /. A hung pass is killed with its process group and reported "hung" with its last tool call. Where there is no bwrap, the log says `"sandbox": "none"`. Codex keeps its own sandbox and disabled features, and gains `--json` logging; its shell being truly off wasn't checked live (Codex is reserved). The screen is Q Branch's, ported as `colony/screen.py`. Its layer 2 runs on the rote tier, else chores, else another model, and holds when there is none. Cross-provider screening is the `room_screen_provider` setting, off by default.

Checked:
- **Unit tests:** 33 in tests/test_room.py, including all of Q Branch's screen cases.
- **(a)** A shell inside the wrapper couldn't open a canary beside it, and /home doesn't exist inside.
- **(b)** A planted page told the pass to read the canary and call out. WebFetch's own summarizer reported the injection and ignored it, /leak was never hit, and the log shows only WebFetch and WebSearch offered. The screen had nothing to cut.
- **(c)** Q Branch's brief ran through it unchanged on Sonnet: 7 searches, 3 fetches, a parseable 1,465-word guide.
- **After the DNS fix,** a real Haiku pass searched, fetched and came back screened. Inside, the board's tailnet name doesn't resolve and example.com does.

Known limits:
- 127.0.0.1 and LAN addresses stay reachable by IP. WebFetch upgrades http to https, which keeps the board's plain http port out.
- Haiku sometimes wraps its screen reply in a code fence, which costs a retry; Claude's `--json-schema` may fix that.
