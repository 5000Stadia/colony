# R162 A link to a project's site is looked at when it is tapped, and colony starts a site that is down

## Where it comes from

A card in the person's Inbox for one project opened another project's site (Nov 12). Two causes were found. The
address had passed from the first project to the second on Nov 9, and the first project's older showcase entries
still carried it. And after the machine restarted the night before, the first project's site was not running at
all, with its agent paused, so the corrected link would have shown an error.

The lead's first repair kept a record of every address ever given, so none would go to another project, and
proposed that colony notice a dead site and tell its project. The person's idea replaced both (three messages in
Chat, Nov 12; their words are kept privately in roadmap/R162.words.md). My reading:

- A link matters only when it is tapped, so that is when it is looked at. Nothing watches sites, and nothing is
  kept about addresses given up: projects and the person both forget old links.
- Healthy, the person is passed through. Down, colony brings the site up itself, in code, as a starting service
  would. No agent has a part in it: a link is used long after its project is parked.
- If it loads, colony's part is done; what is wrong inside a site that loads is between the person and its
  project. If it cannot be loaded, the person is told on a page, with a pointer to the project's agent.

## Shape

- **Every link the board draws to a project's site goes through the opener**, carrying the project the link sits
  in: a showcase entry's Open, an address in a Try or a sign-off's check text, a pinned address. The address as
  the agent wrote it stays in the record; nothing changes in how projects write links.
- **Tapped** (`serving.tapped`):
  - its site answers on this machine: the person is sent on;
  - nothing answers and the project gave a command: colony runs it from the project's folder, apart from the board
    (a unit of its own where systemd runs the person's services, else a process of its own), shows a page that
    asks again every two seconds, and sends them on when it answers. One minute at most;
  - the address is not that project's now (it moved to another port, or another project has it since): the
    project's own site, where it serves exactly one, with the same path;
  - otherwise a page says why (no command, the command did not bring it up, the project serves nothing or several
    sites) and to ask the project's agent.
- **The command** is given once: `colony serve PORT --start 'COMMAND'`. Serving the port again keeps it; `--start
  ''` forgets it. `colony serve PORT` says how when none is set.
- **Taken out:** the record of addresses given up, added the same morning (served-past.json). With the project
  carried in the link, an address reused by another project cannot send a board link to the wrong site.

## Not built, and why

- A link kept outside the board (a bookmark, an icon on a home screen) goes straight to the site and never passes
  colony, so it is not looked at: with the site down it shows Tailscale's own error. Making the address itself
  start its site needs colony to stand at that address while the site is down, which is a larger piece with a
  hazard of its own (a project starting its site by hand would find its port held). Put to the person as a
  proposal.
- A project removed from the board still loses its address, as before. The person's case of a link used after its
  project is removed belongs with the point above.
- Starting sites when the machine starts. Only a tap starts one.

## How it is checked

1. Unit cases (tests/test_board.py, `ServingTest`): another address is left as it is; up, sent on; a second
   project's link to an address that is the first's now opens the second's own site; down with a command, started
   once however often asked, then sent on; never up, said to the person with where to take it; no command; several
   sites; no note reaches any agent; the command kept and forgotten; and over HTTP the redirect, the page that asks
   again, and the 503.
2. On the live board: a site that is up; an old address; a stopped test site started through a nested unit, as the
   real case's command is.
3. The suite passes before the board restarts.

## What was built, and the check's result

- colony/serving.py (`given`, `up`, `start`, `tapped`, the command on a served row), colony/opener.py (`address`),
  colony/board.py (`_address`, used by the opener's route and the two older link routes), `--start` in
  colony/cli.py.
- Check 1: one new test of 28 assertions; the suite passes (1,143).
- Check 2, Nov 12: the live site's link was sent on; the same project's old address, which is another project's
  now, was sent to its own site; a throwaway site with nothing running showed the waiting page, was started by
  colony and opened on the second ask, two seconds later. The first project's own command was registered for it
  (it is the one its notes give for recreating its site), since its agent is paused.
- Not checked live: the real site stopped and started by a tap (it would have interrupted the person, who may be
  using it), and the failure page on a real phone.
