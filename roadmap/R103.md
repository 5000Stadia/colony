# R103 — One colony element through which projects reach outside services

One colony element through which projects reach outside services (first cases: an eBay API connection; SnackStand sending email from its own address). Researched first, thoroughly: the simplest, cleanest, universal, future-proof, safe and free option, easy to pipe new services into for the long term; local only if it stays clean and easy to maintain. The measure is the least effort from the person over the long term. Colony keeps what no off-the-shelf option gives: which project may use which connection, the person's keys kept off conversations and git, and anything that leaves the machine waiting on their tap unless they've said otherwise.

The person, 2026-10-24: "It feels like there should be a colony wide plugin element for these things" … "I want you to look into and consider what you think the simplest cleanest universal future functioning safe and free options is - research thoroughly lets bake it in as a colony element. We also want to consider easy to pipe long term. Local seems nice if its clean and easy if if its less simple to maintain long term then no. Whatever produces the least effort from the user long term". Agent's reading: build it, not just report; the choice between hosted and local is settled by long-term upkeep for him, not by preference. Found while looking: every Claude project here likely sees his personal Gmail (with send and trash) through claude.ai connectors, ungranted; this element closes that.
Built and live (412ee0a): local MCP servers per project, no gateway; keys in owner-only files entered in Settings; held tools run only on the person's tap; their claude.ai connectors granted per project (each keeps what it used). Checked live on Claude Code and Codex. Research: hosted platforms lack eBay selling and Composio leaked keys (May 2026); gateways cost more upkeep than they give. Open: the two first cases, waiting on the person's accounts (an eBay developer keyset; SnackStand's mailbox); Codex's ChatGPT apps not yet per project.
Both first cases prepared, 2026-10-25 (f613d8d, 2032a64): SnackStand's eBay need is its Browse-API watcher (search only), so a connection can now be only keys, which a project's own script runs with (`colony connect --with ebay -- …`), output redacted, nothing held; SnackStand's own mailbox is mcp-email-server 1.13.2 (vetted: annotated tools, no shell-outs, no files in env mode), offering search, read and send, the send held, checked through colony's proxy. Both wait on the person's approval and accounts (gates gfbe408, g47f0e4); once SnackStand's mailbox works, its grant of the person's own Gmail goes off unless they say otherwise. Fixed on the way: a project's own keys couldn't be entered before the connection already worked.
The person, 2026-10-25, on approving a connection: "the approval info is presented without validation of its safety or lack therof ... human will either be glad something bad didnt get auto adopted or adopt blindly even if its bad. It should be auto audited by the steward. With a little report to the user AND listed in the approval area ... if I were to ask an agent 'blindly wire this connector and dont look at its code' and it did the steward would audit it ... Frankly it should just determine if its malicious or unsafe to not allow it and message the agent"; three checks: malice/safety, whether the requesting project's work calls for it, then the person's approval; and "the same agent wiring that has full system permissions… is this performative?" Agent's reading: build the audit as he describes, done by a fresh reader apart from the requesting agent (another model family where available) that reads the pinned package's code, never the agent's account of it, and never runs it; unsafe or incongruent is refused and the agent told, otherwise its report sits in the approval card. Said plainly: against an agent with his full permissions the approval and holds are not a wall (it can read the key files and reach the net itself); they guard against the likelier failures, an agent fooled by what it reads and a poisoned package, and stop a connection spreading to every project. A real wall (agents run without access to the keys) trades away the full permissions he chose, so it is his call (gate).
The audit, built and live 2026-10-25 (ff73d8e): a connection an agent adds is audited before the person is asked. Its pinned package is fetched by digest from PyPI or npm and read, never run, by a fresh reviewer of another family, which judges safe and fits-the-work. Unsafe is refused and the agent told. A poor fit is shown to the person, who may approve anyway: my reading of "incongruent ... investigated and brought to the user", and of what the work needs being theirs to say.
