# R149 What colony needs for a first customer's project

## The person's words

2026-11-02, late evening: "Made me think of what were doing with colony and how we could get a platform like this
primed and prepped for unique projects for unique customers. And as they say “cam we change x or y” that goes through
to the project agent working on it and viola updated"

Then, on the shape: the customer's software is reached as a web app over Tailscale, hosted by the person or on the
customer's own computers, and it is "relatively straitforward flowchart stuff. Get info from x make bid y send to z
for confirmation if update needed so or on confirmation send."

## Reading

The person has a venture of their own: custom workflow software for customers. The venture's specifics stay
private, outside this repository. Colony's part is to be the place this gets built and run:

- Each customer's work is a project on the board, driven by its own agent.
- The customer uses their app as a web app over Tailscale, hosted by the person or on the customer's own computers.
  Either way, Tailscale lets the agent maintain it.
- When the customer asks for a change, the request goes to that agent and comes back done.
- The workflows are flowcharts with a confirmation step: gather information, make a bid, send it for confirmation,
  revise if asked, and send once it's confirmed. That's a common enough shape that a base can be primed for it.

## What colony lacks today (the agent's reading)

- **A customer's view.** The board is the keys to everything. A customer reaches only their app and a place to ask
  for changes.
- **Isolation.** A customer's request becomes text that an agent with tools acts on. Each customer project needs a
  sandbox, walled off from the person's own projects and data (the same idea as R147).
- **Customer data.** Build on sample data. Real customer data stays in the deployed app.

## How it gets built

Built for problems the first real project shows. Nothing gets designed up front.

1. The first customer is served with colony as it is: a project on the board, their app shared over Tailscale, and
   their requests relayed by the person.
2. Each gap that shows up gets built here.
3. The second customer shows what's shared between them, and that shared part becomes the primed base.

## The platform's shape, from brainstorming with the person (2026-11-03)

- **Where a space runs.** The person: "I dont need to own it … would rather it be on their machine or cloud". So the

  - the customer's own box (a small dedicated machine, not their everyday computer);
  - a small cloud server per customer;
  - a tucked-away mini that the person hosts, separate from the colony desktop, with one virtual machine per

  The package is the same everywhere, so a customer can move from one place to another.
- **Everything moves by pulling.**
  - The space pulls its own code updates.
  - Colony fetches change requests from the space, and they land as notes on that customer's project.
  - The person's desktop holds no keys to customers' spaces, and spaces never reach each other.
- **How the customer gets in, chosen per customer:** a Tailscale share of their one machine, or a login page with
  an emailed code and nothing to install.
- **Commercial use needs Tailscale's paid plan** (research library rce8db123).

## The split, decided (2026-11-07)

The person agreed with the split and asked me to write to their business project explaining the shape both
projects need to fit together as fully as possible (gate gfb53f95d). Their words are in R149.words.md, kept on this machine, out of the public repository.

My reading: separate, but built to fit as one. I sent that project the shape (mail m848cab2c):

- **One family on the board.** Their business project becomes a nest, with the starter base and each customer's
  project as its nestmates.
- **A customer project starts from the base.** Colony adds starting a new project from a base repository.
- **The request box is where they meet.**
  - The customer's app holds change requests.
  - Colony pulls each box over Tailscale, and each request lands as a note on that customer's project, marked as
    the customer's words, not the person's direction.
  - Status goes back to the app.
  - Colony's access is scoped to the box, and colony stores no customer data.
- **The person authorizes with a gate.** On a yes, the project tags a release, and the app's updater pulls only
  authorized releases, overnight, with a self-check and rollback.
- **Walled off.** A customer project writes only to the business project and the base, and its sandbox sees only
  its own folder. This is built before any real customer's text reaches an agent.
- **Lessons flow upward** to the base. Colony receives only general ones.
- **No shared code.** The customer's app never imports colony and runs with colony off.

The order: the box's contract first, agreed when their starter base begins (I draft it, they check it against real
needs). Then starting from a base and the walls, with the first customer project. The bridge comes when the first
customer app is live.

### Contract v1: draft 2, agreed 2026-11-07 (mail m60c5302c)

The business project builds its side against this. Colony builds the bridge when that project's first client
project is ready to start from the base. It isn't near: the customer app is at its first step, and a client's
build waits on a paying yes. The business project will say when one is coming.

It checked draft 1 (mail mfbed76ed) against its customer app and a prospective customer, and found it fits.
It asked for five changes, all taken:
1. **Signed releases.** A tag alone isn't enough: the client project's agent can write to its own repository, so it
   could push one. Now only a signature from colony's bridge makes a release.
2. **Alert events.** The box is the space's only way to reach the person, so outages, a quiet flow, a failed backup,
   a cost cap and a missed install window come through it.
3. **Author ids**, since names change and two staff can share one.
4. **Attachments on the person's messages** (a screenshot of the change, a photo, a PDF).
5. **The install window in `health`**, so the time colony shows matches what the space will do.

I added three things: a `release_refused` event, so a refused tag is reported; no repeat alert while one of the same
kind is still open; and the space states its upload limit. A `preview_url` on `drafted`, so the owner can try a
change before the person authorizes it, comes later, as an added field.

Agreeing to draft 2, it added `seq` in the signed tag, so an old signed tag pushed again under a new name can't
make a space reinstall an old release. On its side, the box listens only on the tailnet address, never on the
staff sign-in page.

**Where it runs.**
- The space serves the box on the tailnet at `/colony/box/v1/`. Colony pulls from it, and the space never calls
  colony.
- One bearer token per space is scoped to the box alone. Colony's bridge keeps it with colony's secrets, never in a
  project or an agent's reach, and the space can revoke it.

**Endpoints.**
- `GET /colony/box/v1/health` returns `{contract: "1", release, seq, ok, install_window {start, end, tz},
  max_upload_bytes}`. The owner sets the window in the space.
- `GET /colony/box/v1/feed?after=<cursor>` returns `{items: [...], cursor}`, oldest first. Each item has an `id`
  (stable, assigned by the space), `at`, `type` and `thread`. The types are:
  - `request`: `author {id, name, role}`, `text`, `urgent`, `in_reply_to?`, and `attachments [{ref, kind, name,
    bytes}]`. The kinds are photo, screenshot, audio, file and record (a record the person handed over, point 6).
    An optional `page {path, name}` is the board page it was written from, as the space names it (`{"path":
    "/items/12/", "name": "Jobs › Gutters, 9 Oak Ave"}`). It's present only when the writer left it ticked, and
    the space names only a page that writer may open. (Added by the business project, Nov 8, mail md57d5159.)
    An optional `where {kind, section, part}` says what the writer picked before writing: `kind` is `change`,
    `new_part`, `new_section` or `other`, and `section` and `part` are the board's own names. The bridge puts it in
    the note's header as it does the page, so `text` stays the writer's words alone. (Added by the business project,
    Nov 12, mail md61ea89a; colony's answer the same day.)
  - `event`: `what` and `detail`. These are:
    - releases: `release_installed`, `release_rolled_back`, `release_refused` (unsigned or an unknown key, with the
      tag) and `self_check_failed`;
    - `askers_changed`, with author ids;
    - alerts: `connection_down` (with connector, account and `reason`: down, needs_reconnect or expiring),
      `flow_quiet` (with the flow and how long it's been quiet), `backup_failed`, `cost_cap_near`,
      `cost_cap_reached` and `update_window_missed`. `flow_quiet` comes in two kinds (mail m36b2e8c5, Nov 9, added
      within v1): quiet (`quiet_hours`, `normal_hours`, `last_ran`) and failing (`failing: true`, the flow's name, and
      for a timed flow `attempts`, `error` as the exception's type only, and `occurrence`). A timed flow that kept
      failing, a monthly note that couldn't be made, or a staff-email flow with no mailbox connected raise the failing
      kind. Each carries `alert`, the space's id for that open alert. A
      change the person must act on differently (a down that now needs a reconnect) is a new alert, with a new id;
    - `alert_closed`, with `alert` and the alert's `kind`, which closes any alert. A failed backup closes on the
      next good run, and a missed install window on the next release tried. `connection_restored`, with the connection's last open
      `alert`, closes that one.
- `GET /colony/box/v1/attachments/<ref>` returns the file. It's fetched only on the agent's request.
- `POST /colony/box/v1/attachments`, from the person, takes the file, its `name`, `kind` and a `key`, up to
  `max_upload_bytes`, and returns `{ref}`, in the same ref scheme. It lives in the space like the customer's
  attachments.
- `POST /colony/box/v1/messages`, from the person, takes `{key, thread, text, kind: reply|question, in_reply_to?,
  attachments: [ref]}` and returns `{id}`. `key` makes a retry safe. The person's messages aren't echoed back into
  the feed: colony keeps its own copy of what it sent.
- `POST /colony/box/v1/status` takes `{key, item, status, note?, at?}` and returns `{item, status}`. The statuses:
  - automatic: `received`, `drafted`, `waiting_on_person`, `scheduled` (with `at`, ISO 8601 with its offset, from
    the install window; without it the space shows its own window), `done` and `rolled_back`;
  - only with the person's words or yes: `asked_you`, `quoted` and `not_now`.
  - An unknown status is refused (400), so a new status is a contract change, not an added field.
- Ids, as the space assigns them: a feed item's id is its position as a string, and the cursor is the same number.
  The person's messages are `k<n>`, and authors are `s<staff id>`. A request's thread is its own id, or the thread
  of the question it answers. A connection's events share the thread `connection-<id>`. `askers_changed` carries
  `{askers: [{id, name, role}]}`.

**On colony's side.**
- Each request becomes a note on that customer's project: "from <customer>, written by <name, role>", with "about
  <page name>" when it carries a page, marked as the customer's words. It's data, never the person's direction. The
  page's path goes with it, so the agent can find that page in the client's code.
- An urgent request wakes the agent and tells the person at once.
- The person's picture of the whole path, as the business project relayed it (Nov 12, mail mcf98478d; their words
  are in that mail): a client's request reaches that client's agent, which opens a Needs you item for the person;
  they answer it with the agent; once they approve, the fix or the reply goes back to the client's own messages.
  My reading: the contract as it stands, with one emphasis: every request ends as an item in the person's Inbox,
  not only as a note the agent reads.
- An alert tells the person at once and lands on the customer's project as a note, once per `alert` id. A failing
  `flow_quiet` reads to them as a failure ("failing"), never as a quiet flow. A repeat of
  an open id doesn't tell them again. Its close (`alert_closed` or `connection_restored`) clears it on the board
  without a ping.
- The agent gets an attachment with a colony command. The file lands in the customer project's own folder, inside
  its walls, and is deleted when the item closes. A handed-over record is treated the same way.
- Everything the customer sees from the person goes through a gate or the person's own typing. The agent drafts
  and never sends.
- Notes and fetched files live only in the customer project's own records and folder, never in colony's store or
  repository. Customer projects' repositories are private, and anything they report to colony carries only the
  general lesson.

**Releases.**
- These are separate from the box. On the person's yes, colony's bridge makes an SSH-signed tag in the customer's
  private repository. The signing key is the bridge's alone, kept with colony's secrets, outside every project's
  reach. The bridge signs only for a gate the person answered.
- The tag's message carries the gate, the items, whether it's urgent, and `seq`, a release number that only goes
  up. So the agent can't make a release, or make one urgent, or replay an old one under a new name.
- At setup, the space pins the bridge's public key. Its updater installs only tags that verify against that key
  (`git verify-tag` with the pinned signers file), whose name matches the ref, and whose `seq` is above the highest
  it has tried. Any other tag is never installed and is reported as `release_refused`.
- The tag's message, exactly (agreed with the business project, mail mbbaebffa):
  ```
  colony-release 1
  seq: 7
  gate: g1234abcd
  items: R3 R4
  urgent: no
  ```
  The first line is the format and its version. Then come `key: value` lines: `seq` is a positive whole number,
  `items` are space-separated, and `urgent` is yes or no. Unknown keys are ignored, so it grows by adding fields. A
  repeated key, a missing one, or any other first line is refused. The tag is annotated, SSH-signed and points at a
  commit. Its name can be anything (`release-<seq>`), but the name inside the signed object must match the ref. The
  space pins the key as an allowed-signers line with `namespaces="git"`. Two signed tags with the same `seq` are
  both refused.
- The gate pins the commit the person reviewed. It records the commit its diff was made from, and the bridge signs
  that commit, never the branch's head at signing time. A push to the branch after the gate opens voids the gate: it
  is asked again with the new diff. (Memory Research's note of Nov 8, mail m18352395, after GitHub's "dismiss stale
  pull request approvals when new commits are pushed". The signed tag already names its commit, so the space's side
  doesn't change.)
- A release that failed its self-check isn't tried again. A deliberate rollback, or the fix, is a new signed tag
  with a higher `seq`, pointing at the commit it should run.
- A new key is pinned in the space at setup, by hand, never through the box.
- The updater installs in the owner's install window. A signed urgent tag installs at once.
- The self-check and rollback are the space's. It reports each outcome as an `event`.

**Trust.**
- Colony polls every minute.
- A revoked token, or a space unreachable for an hour in the owner's working hours, tells the person.
- Nothing waiting to go out is lost: a write that fails is kept and retried under its `key`.
- Within v1, changes only add fields.

## The release signer and the walls, sharpened (2026-11-09, mail m525e10dc)

The business project ran a consult on keeping clients' spaces apart and sent the three points that land here. I
checked each against colony as it runs.

**What I checked.**
- The board, colony's commands and every project's agent run as one Unix account. Colony's secrets folder is
  readable by that account.
- A gate's answer is a line appended to the project's own `.board/gates.jsonl`. That file sits inside the project's
  folder, so the project's agent can write it, with or without walls.

So two lines of the contract above didn't hold as written: the key "outside every project's reach", and a bridge
that "signs only for a gate the person answered". A steered client agent could write the answer itself, and with no
walls it could read the key. A signed release is code that runs beside a business's records, so this is the part
that has to hold.

**What changes in the design.**
1. **The yes is one no agent could have written.** The bridge never signs on a line in a project's records. It signs
   on a yes made on the person's own device for that exact release: a passkey assertion over the commit, `seq` and
   urgency, taken on the board's release page. The board only carries it. The signer checks it itself.
2. **The signer runs where no agent runs.** The bridge (the poller that holds each box's token, and the signer that
   holds the key) runs under its own Unix account, or signs with a hardware key that needs a touch. The board and the
   agents reach it through one narrow door that takes a repository, a commit, a `seq`, a gate and the assertion, and
   gives back a tag or a refusal.
3. **What the person reads at the release gate isn't only the agent's summary.** The bridge makes part of it from
   the commit itself: the files touched and any new outside address. (The business project adds the same on its
   side.)

**The walls.**
- They are an operating-system boundary for each client project, not a provider's permission setting: R147's room
  (bubblewrap, seeing only the project's folder, never `/`), under an account of the client project's own or in a
  container, so a run started without the wrapper still can't read another client's folder or colony's secrets.
- They cover every agent and helper that reads a client's text, and they stand before the first client's text
  reaches one.
- A walled agent has no route to the tailnet. Only the bridge reaches a space.
- A client project's own records are inside its walls, so its agent can write them. Nothing with an effect outside
  that project is decided from them: its mail is data to whoever reads it, and its gates authorize nothing beyond
  its own folder.

**The tailnet.**
- Each space is its own node with its own tag. The grants let the bridge reach each space's box port and nothing
  else, and let a space reach nothing. SSH stays off in spaces, Tailscale's included.
- This narrows an earlier line of this item: the agent never maintains a space over Tailscale. A space pulls its
  signed releases, and the bridge pulls its box.
- The paid plan was already known (research library rce8db123). The business project asks the person about it when
  its first client space is near, so colony doesn't ask twice.

**Open, the person's.** A passkey yes means a tap on their phone for each release. Whether releases work that way
is before them on the business project's side (its gate g44fb5af7), and colony's bridge follows their answer. My
recommendation is yes: a release is rare, and it is the one step where a forged yes would run code at a client's.

**Check, when it's built.** A client agent that writes an answer into its own records and asks for a release gets no
tag. A process under an agent's account can't read the key or a box's token. A walled agent can't open another
client's folder, colony's secrets or a tailnet address.


## Asked of the bridge: the change in the client app's own words (2026-11-13, mail mbf8f511f)

The business project asks that the release gate carry one more thing the bridge makes from the commit itself, beside
the files touched and new outside addresses (point 3 above): the client app's own account of what the release
changes for its owner, made by a command its repository provides, comparing the installed release with the gate's
commit, and shown whole and unedited. Its reason is the design's own: these are the words the approver reads, so the
agent must not be the one who writes them. Until the bridge exists the client's agent pastes that output and the
gate says the agent made it.

Not built: it rides with the bridge, which waits on a first client. My view, sent back to them (not a decision):

- **Which copy of the command runs matters more than whether the bridge can run one.** A command taken from the
  gate's commit is code the client's agent wrote, and could print anything. The bridge runs the copy from a release
  already approved (the installed one, or the base's own signed version) and gives it the new commit as data only.
- **Not under the signer's account.** It runs under a third account with no key, no token and no network, reading
  the checkout and nothing else; the signer only receives its output. A failure or a non-zero exit is shown as that,
  and the gate says the account could not be made.
- **Its form.** The text is what the person reads, whole. A small machine-readable part beside it (the kind of
  change) lets the gate mark the kind that needs reading without colony interpreting prose.

**Check, when it's built.** A commit that changes the command itself so it prints a harmless account still shows the
true change, because the copy that ran was the approved one.
