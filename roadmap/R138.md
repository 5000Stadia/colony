# R138 — A helper never wakes its lead just to say it is still waiting

A helper never wakes its lead just to say it is still waiting. The person, 2026-10-31, on hearing the lead was woken 15 times that day by helpers' "still waiting on its own background work" notices (5.9 million tokens of re-reading): "There has to be a no real token way to identify \"still waiting\" even if it's an interim space gating passing information back until it's certainly done. The cheapest model here is better than it getting back to the primary agent, but even better there has to be a near zero token mechanism for this". Agent's reading: the waiting belongs in a shell, which costs nothing, not in any model. Two parts: (1) the full suite runs its files side by side, finishing well inside the 10-minute limit on one command, so a helper waits for it within one step and never stops mid-wait (it also cuts every deploy's wait from about 12 minutes); (2) for any other long background work, if Claude Code allows it, a hook at a helper's stop holds the stop in a shell while its own background command runs, then lets it continue with the result, so the lead hears once, when the helper is done. Check: the parallel suite passes three times with the serial count; then a day of helper work with no "still waiting" notices reaching the lead. Part 1 built and live 2026-10-31 (8ac55ba): tests/run.py runs the whole suite in 77 s on 12 workers, against 649 s serial; three parallel runs matched each module run alone, test for test (1026 then; 1039 on the merge with main, which passed in 77 s); CLAUDE.md, AGENTS.md and README point to it, and a test now checks the plain command lists every tests/test_*.py. Part 2 (the stop hook), per the docs check: possible (SubagentStop can block with a reason; command hooks default to 600 s with no stated maximum), but whether holding the stop suppresses the lead's notice is undocumented; built only if "still waiting" notices still reach the lead now that the suite fits in one command.
